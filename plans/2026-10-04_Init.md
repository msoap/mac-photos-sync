# Apple Photos Hard-Link Sync — Implementation Plan

## 1. Goal

Implement a command-line synchronization tool in Go that creates a filesystem-oriented mirror of an Apple Photos library.

The mirror must:

- never modify the source Photos library;
- use hard links instead of copying media files;
- organize media by capture date;
- preserve the original imported filename when it can be recovered;
- distinguish edited versions from originals;
- store Live Photo companion videos separately under `live/`;
- maintain a SQLite metadata catalog in the destination root;
- support incremental synchronization;
- remove destination hard links when the corresponding source asset/file disappears;
- be recoverable using only:
  - the source Photos library;
  - the destination directory.

The destination SQLite database is an index/catalog of the synchronized state. It may be used to optimize synchronization, but it must not be the only source of truth for deciding what physically exists.

The implementation language must be Go.

---

## 2. Command-Line Interface

Implement a CLI:

```text
photos-sync [options] <destination>
```

Options:

```text
-library <path>
    Path to the Apple Photos library.

    Default:
    ~/Pictures/Photos Library.photoslibrary

-dry-run
    Show planned filesystem/database changes without applying them.

-verbose
    Print detailed synchronization information.

-rebuild-db
    Rebuild the destination metadata database from the current source and
    destination state.

-workers N
    Number of concurrent metadata extraction workers.

-help
    Print usage.
```

Example:

```bash
photos-sync ~/PhotosMirror
```

Explicit Photos library:

```bash
photos-sync \
    -library "/Volumes/Photos/Photos Library.photoslibrary" \
    ~/PhotosMirror
```

The source library must always be treated as read-only.

---

## 3. Destination Layout

Organize media by capture date:

```text
DEST/
    photos.sqlite

    2024/
        2024-03/
            2024-03-18/
                IMG_1234.HEIC
                IMG_1235.JPG
                IMG_1236.MOV

                orig/
                    IMG_1234.HEIC

                live/
                    IMG_1234.MOV
```

General layout:

```text
YYYY/
    YYYY-MM/
        YYYY-MM-DD/
            <current photos and normal standalone videos>

            orig/
                <original media for edited assets>

            live/
                <Live Photo companion videos>
```

Rules:

- normal photos are stored directly in the day directory;
- normal standalone videos are stored directly in the day directory;
- current edited versions are stored directly in the day directory;
- unmodified originals for edited assets are stored under `orig/`;
- Live Photo companion videos are stored under `live/`;
- `orig/` is created only when needed;
- `live/` is created only when needed;
- empty date directories must not be created.

---

## 4. Critical Design Rule: Read-Only Source

The source `.photoslibrary` package must never be modified.

The program must not:

- write to `Photos.sqlite`;
- modify SQLite WAL/SHM files;
- modify media;
- rename source files;
- change source permissions;
- create files inside the library;
- invoke Photos.app APIs that modify the library.

Open source media read-only.

Open the Photos database using SQLite read-only mode.

Because Photos may have:

```text
Photos.sqlite
Photos.sqlite-wal
Photos.sqlite-shm
```

do not blindly copy, delete, truncate, checkpoint, or otherwise manipulate these files.

During the investigation phase determine the safest method for obtaining a consistent read-only SQLite view while Photos.app may be running.

If reliable concurrent reading cannot be guaranteed, document that Photos.app should be closed while synchronizing.

## 5. Phase 1 — Photos Library Investigation

Before implementing synchronization logic, inspect the actual Photos library and document its layout and schema.

Do not assume Apple's private Photos schema is stable.

Create:

```text
docs/photos-library.md
```

Document:

- macOS / Photos database version if detectable;
- location of `Photos.sqlite`;
- important tables;
- relevant columns;
- relationships between assets and resources;
- location of originals;
- location of edited/rendered resources;
- Live Photo representation;
- standalone video representation;
- RAW+JPEG representation;
- filename mappings;
- UUID mappings;
- deleted/trashed asset representation.

Start with:

```text
<library>/database/Photos.sqlite
<library>/originals/
<library>/resources/
```

For modern Photos versions, investigate at least:

```text
ZASSET
ZADDITIONALASSETATTRIBUTES
ZINTERNALRESOURCE
```

Inspect the schema:

```sql
SELECT name
FROM sqlite_master
WHERE type = 'table'
ORDER BY name;
```

and:

```sql
PRAGMA table_info(ZASSET);
PRAGMA table_info(ZADDITIONALASSETATTRIBUTES);
PRAGMA table_info(ZINTERNALRESOURCE);
```

Do not implement final production SQL queries until the actual database schema has been examined.

The first implementation milestone is understanding and documenting the actual library rather than immediately writing synchronization logic.

## 6. Determine Asset → Physical File Mapping

Determine exactly how a logical Photos asset maps to physical files.

For each asset determine:

```text
asset UUID
original filename
physical original path
physical edited/rendered path, if any
Live Photo companion path, if any
media type
capture date
modification state
```

Investigate fields such as:

```text
ZASSET.ZUUID
ZASSET.ZDIRECTORY
ZASSET.ZFILENAME
```

and whether the original imported filename can be obtained from:

```text
ZADDITIONALASSETATTRIBUTES.ZORIGINALFILENAME
```

These names are starting points for investigation, not guaranteed schema contracts.

The implementation must validate database-derived information against actual files.

For every database-derived source path perform an equivalent of:

```go
os.Stat(path)
```

before using it.

Never assume that a database resource is locally available.

---

## 7. Recover Original User Filename

The destination should use the original imported filename whenever possible.

Example:

```text
Photos physical file:
originals/A/A12B34....HEIC

Photos database:
ZORIGINALFILENAME = IMG_4821.HEIC

Destination:
2025/2025-07/2025-07-14/IMG_4821.HEIC
```

Use this priority order:

1. original filename stored in `Photos.sqlite`;
2. metadata containing an original filename, if available;
3. useful embedded filename metadata;
4. physical source filename as the last fallback.

Do not assume EXIF normally contains the original filesystem filename.

Record how the filename was obtained:

```text
filename_source =
    photos_database
    metadata
    filesystem
```

Preserve the original filename's extension.

Do not force files to `.jpeg`.

Examples:

```text
IMG_1001.HEIC
IMG_1002.JPG
IMG_1003.MOV
IMG_1004.CR3
```

---

## 8. Filename Collision Handling

Multiple assets may have the same original filename and capture date.

Never overwrite or replace another asset.

Use deterministic collision names:

```text
IMG_0001.JPG
IMG_0001_2.JPG
IMG_0001_3.JPG
```

The assignment must be deterministic between runs.

Prefer preserving an already-established destination filename when it still represents the same source resource.

The database must record:

```text
original_filename
destination_filename
```

Collision handling must work independently inside:

```text
day/
day/orig/
day/live/
```

Never resolve a collision by replacing an existing unrelated file.

---

## 9. Date Selection

The directory date should represent the actual media capture date.

Determine it using this priority:

1. Photos database capture date;
2. EXIF `DateTimeOriginal`;
3. QuickTime creation metadata for videos;
4. other embedded creation timestamp;
5. filesystem timestamp only as a final fallback.

Store:

```text
capture_time
capture_time_source
timezone_offset
```

Do not silently use source filesystem modification time as the photo capture date.

Photos timestamps may use Apple's epoch rather than the Unix epoch. Implement conversion explicitly and test it.

Be careful with:

- timezone information;
- timestamps without timezone;
- historical photos;
- imported photos with manually corrected dates.

---

## 10. Edited Photos

Determine how Photos represents edited assets.

Desired behavior:

```text
2024/2024-03/2024-03-18/
    IMG_1234.JPG

    orig/
        IMG_1234.JPG
```

For an edited asset:

```text
day/IMG_1234.JPG
```

must represent the current edited/full-size version that the user sees in Photos.

```text
day/orig/IMG_1234.JPG
```

must represent the unmodified original.

For an unedited asset create only:

```text
day/IMG_1234.JPG
```

Do not create:

```text
day/orig/IMG_1234.JPG
```

if it would simply be another hard link to the same unmodified resource.

Before implementing this behavior, inspect the actual database/resource relationships.

Determine:

```text
asset
    -> original resource
    -> current/full-size adjusted resource
```

Ignore:

- thumbnails;
- previews;
- caches;
- low-resolution derivatives;

unless investigation proves that a particular resource is the only full-quality representation required for the mirror.

---

## 11. Live Photos

Explicitly investigate Live Photos.

A Live Photo normally consists logically of:

```text
image
video companion
```

They must be represented as resources belonging to one logical asset:

```text
Asset
├── image resource
└── Live Photo video resource
```

The image is stored normally:

```text
2024/2024-03/2024-03-18/IMG_1234.HEIC
```

The companion video is stored under:

```text
2024/2024-03/2024-03-18/live/IMG_1234.MOV
```

Complete example:

```text
2024/
    2024-03/
        2024-03-18/
            IMG_1234.HEIC

            live/
                IMG_1234.MOV
```

The `live/` directory must be created only when the day contains at least one Live Photo companion video.

Classify the companion video explicitly:

```text
resource_type = live_photo_video
```

A Live Photo companion video must:

- remain associated with its image asset;
- not be represented as an independent Photos asset;
- not be placed directly in the day's root directory;
- preserve its original filename where possible.

Do not assume that the Live Photo MOV always has exactly the same basename as the image.

Determine the association from Photos database/resource metadata.

For an edited Live Photo, investigate the relationship between:

```text
adjusted image
original image
Live Photo companion video
```

before deciding which physical resources to expose.

---

## 12. RAW and Multi-Resource Assets

Investigate assets containing combinations such as:

```text
RAW + JPEG
Live Photo image + MOV
edited JPEG + original RAW
```

Do not discard secondary full-quality resources.

Model these as one logical asset with multiple resources.

Each physical destination file must have its own resource record in SQLite.

The model must therefore explicitly distinguish:

```text
logical Photos asset
```

from:

```text
physical media resource
```

Never assume:

```text
one asset == one file
```

---

## 13. Hard-Link Requirements

Use:

```go
os.Link(source, destination)
```

Never copy media during normal synchronization.

Before creating a hard link, verify that source and destination are on filesystems where hard linking is possible.

Handle:

```text
EXDEV
```

explicitly.

If source and destination are on different filesystems, abort with a clear error:

```text
cannot create hard links: source and destination are on different filesystems
```

Do not silently fall back to copying.

---

## 14. Verify Existing Hard Links

Do not assume that a destination file with the expected filename is the correct link.

Verify source and destination identity using filesystem metadata.

On Unix/macOS compare:

```text
device ID
inode number
```

A correct hard link must refer to the same inode.

If a destination path exists but refers to another inode:

- do not overwrite it blindly;
- determine whether it is a stale managed file or an unrelated user file;
- managed stale files may be repaired;
- unrelated files must be reported as conflicts.

Implement filesystem identity checks in a dedicated package.

---

## 15. Never Delete Unknown User Files

Synchronization may delete only files that can be confidently identified as files managed by this program.

Never recursively force the destination directory to exactly match the generated model by deleting arbitrary files.

For example:

```text
DEST/notes.txt
DEST/2024/manual.txt
DEST/2024/2024-01/2024-01-01/notes.txt
```

must not be deleted.

A destination media file can be considered managed when it can be correlated with:

- a database resource record;
- and/or a hard link to a known Photos resource;
- and/or other sufficiently strong synchronization identity.

Document the exact ownership rule before implementing deletion.

When ownership cannot be confidently established, report a conflict rather than deleting the file.

---

## 16. Incremental Synchronization

Every execution should compute:

```text
SOURCE STATE
vs
DESTINATION STATE
```

and produce a synchronization plan.

Possible operations:

```text
CREATE_LINK
REMOVE_LINK
MOVE_LINK
REPAIR_LINK
UPDATE_METADATA
NOOP
CONFLICT
```

The destination SQLite database may make this faster, but correctness must not depend entirely on it.

If `photos.sqlite` is deleted, running the tool again must be able to reconstruct it.

A second synchronization with no changes should perform zero media filesystem mutations.

---

## 17. Source Deletions

If an asset/resource no longer exists in the source library, remove the corresponding managed hard link from the destination.

This includes:

```text
primary image
edited version
original under orig/
Live Photo video under live/
standalone video
RAW/paired resources
```

Do not treat Photos "Recently Deleted" state automatically as physically deleted until its representation has been investigated.

Recommended policy:

Synchronize only live Photos assets and exclude items marked as trashed/Recently Deleted.

Document and test the exact behavior.

---

## 18. Detect Date Changes

Photos metadata can change even when the physical original does not.

For example:

```text
old:
2024/2024-03/2024-03-10/IMG_1234.JPG

new:
2024/2024-03/2024-03-11/IMG_1234.JPG
```

Move all associated resources together where applicable:

```text
IMG_1234.JPG
orig/IMG_1234.JPG
live/IMG_1234.MOV
```

Because these are hard links, implement the move safely as:

1. create the new hard link;
2. verify source/destination inode identity;
3. unlink the old destination path.

Never rename or otherwise modify the source file.

---

## 19. Metadata Extraction

Use two metadata backends.

### Primary Backend: Pure Go

First evaluate:

```text
github.com/bep/imagemeta
```

The required coverage includes, where supported:

- EXIF;
- IPTC;
- XMP;
- JPEG;
- TIFF;
- HEIF/HEIC;
- relevant RAW formats.

Create an internal abstraction:

```go
type MetadataReader interface {
    Read(path string) (*Metadata, error)
}
```

The rest of the program must not directly depend on a particular EXIF library.

### Fallback Backend: ExifTool

Support ExifTool when the pure-Go parser cannot provide adequate metadata, particularly for:

- MOV;
- MP4;
- QuickTime metadata;
- unusual RAW formats;
- Apple-specific metadata.

Do not spawn a new `exiftool` process for every file in a large library.

Prefer:

- ExifTool `-stay_open`;
- or batched requests.

Evaluate:

```text
github.com/barasher/go-exiftool
```

The application should still work without ExifTool for formats supported by the pure-Go backend.

type Metadata struct {

## 22. Database Model

Use at least:

```text
assets
resources
sync_info
```

### `assets`

Suggested schema:

```sql
CREATE TABLE assets (
    id INTEGER PRIMARY KEY,

    photos_uuid TEXT NOT NULL UNIQUE,

    original_filename TEXT,
    capture_time TEXT,
    capture_time_source TEXT,
    timezone_offset INTEGER,

    media_type TEXT,

    width INTEGER,
    height INTEGER,
    duration_ms INTEGER,

    latitude REAL,
    longitude REAL,

    favorite INTEGER,
    hidden INTEGER,

    metadata_json TEXT,

    synced_at TEXT NOT NULL
);
```

### `resources`

Suggested schema:

```sql
CREATE TABLE resources (
    id INTEGER PRIMARY KEY,

    asset_id INTEGER NOT NULL,

    resource_type TEXT NOT NULL,

    source_path TEXT NOT NULL,
    destination_path TEXT NOT NULL,

    original_filename TEXT,
    destination_filename TEXT,

    size INTEGER,
    device INTEGER,
    inode INTEGER,

    metadata_json TEXT,

    FOREIGN KEY(asset_id) REFERENCES assets(id)
);
```

Possible resource types:

```text
original
adjusted
live_photo_video
raw
paired_image
video
other
```

Store destination paths relative to the destination root where practical.

## 23. Full-State Database Semantics

After a successful synchronization, `photos.sqlite` must describe the complete current synchronized state.

It must not behave as an append-only event log.

For every current destination resource store:

```text
Photos asset UUID
resource type
source path
destination path
original filename
destination filename
capture date
file size
device/inode identity
metadata
```

Deleted resources must be removed from the current-state tables.

The database should make it easy to query the complete current mirror without rescanning the filesystem.

---

## 24. Database Is Rebuildable

Implement:

```text
-rebuild-db
```

The database must be considered disposable.

This scenario must work:

```bash
rm DEST/photos.sqlite
photos-sync DEST
```

Expected result:

- existing correct hard links are detected;
- unnecessary links are not recreated;
- `orig/` resources are recognized;
- `live/` resources are recognized;
- metadata is re-extracted as necessary;
- `photos.sqlite` is reconstructed.

Loss of the catalog database must never require rebuilding the media mirror from scratch.

---

## 25. Synchronization Pipeline

Implement synchronization in distinct phases.

### Phase A — Discover Source

Read `Photos.sqlite` and produce:

```text
[]Asset
    []Resource
```

Do not modify the filesystem.

### Phase B — Validate Source Resources

For every expected resource:

```text
stat source
validate existence
record device/inode/size
```

Missing local resources must be reported.

This is particularly important when iCloud Photos uses Optimize Mac Storage.

Never attempt to download missing iCloud originals automatically.

### Phase C — Compute Destination Paths

Determine:

```text
capture date
YYYY/YYYY-MM/YYYY-MM-DD
filename
root/orig/live placement
collision suffix
```

### Phase D — Scan Destination

Collect:

```text
path
device
inode
size
```

### Phase E — Diff

Compute:

```text
create
remove
move
repair
metadata-update
conflict
```

Do not mutate the filesystem while still discovering the desired state.

### Phase F — Apply Filesystem Changes

Use a safe order:

1. create required directories;
2. create new hard links;
3. verify new hard links;
4. remove obsolete managed links;
5. remove empty `orig/`, `live/`, and date directories;
6. update SQLite.

Avoid destructive operations before replacement links have been successfully created.

### Phase G — Commit Database State

Write the new complete database state transactionally.

---

## 26. Crash Safety

Synchronization must tolerate interruption.

Do not update the database to claim that a filesystem operation succeeded before the operation actually succeeds.

Prefer:

```text
filesystem mutation
        |
        v
filesystem verification
        |
        v
database transaction
```

After interruption, the next execution must reconcile actual filesystem state rather than blindly trusting an incomplete database state.

Use SQLite transactions.

---

## 27. Metadata Extraction Performance

Avoid reading entire media files into memory.

Use bounded concurrency.

Suggested architecture:

```text
source discovery
      |
      v
metadata job queue
      |
      +---- worker
      +---- worker
      +---- worker
      +---- worker
      |
      v
normalized metadata
```

Do not extract metadata again when the resource can confidently be identified as unchanged and valid metadata already exists.

Potential cache identity:

```text
device
inode
size
```

Additional timestamps or other identity information may be used if needed.

Correctness must never depend on the metadata cache.

## 34. Error Handling

Differentiate fatal and non-fatal errors.

Fatal examples:

```text
Photos.sqlite cannot be opened
destination cannot be written
source and destination filesystems differ
unsupported Photos database schema
catalog database cannot be committed
```

Potentially non-fatal resource errors:

```text
original is not locally available
Live Photo companion is not locally available
metadata cannot be parsed
unsupported metadata format
broken Photos resource reference
```

Continue synchronization where safe.

Return a non-zero exit status when synchronization is incomplete or encountered errors requiring user attention.

## 35. iCloud / Optimize Mac Storage

Apple Photos may use:

```text
Optimize Mac Storage
```

The database may therefore describe an asset whose original physical resource is not locally available.

Distinguish:

```text
asset exists in Photos database
```

from:

```text
media resource exists locally
```

This applies independently to Live Photo resources.

For example:

```text
image locally available
MOV companion not locally available
```

is a valid state that must be handled explicitly.

Do not create broken links.

Report missing local resources.

Do not ask Photos.app or iCloud to download anything.

## 39. Acceptance Criteria

The project is complete when all of the following hold:

### Project and Build

- The project is implemented in Go.
- `main.go` is located in the project root.
- `Makefile` is located in the project root.
- `make build` produces:

```text
./photos-sync
```

- `make build-amd64` cross-compiles for:

```text
GOOS=darwin
GOARCH=amd64
```

and produces:

```text
./photos-sync-amd64
```

- `make install` uses:

```bash
go install .
```

and installs the application under the Go-configured `$GOPATH/bin`.

- The project avoids CGO dependencies where practical so macOS AMD64 cross-compilation remains straightforward.

### Source Safety

- The source Photos library is never modified.
- Source SQLite files are never modified.
- Source media files are never modified.
- Media data is never copied during normal synchronization.

### Destination

- Destination media files are hard links to source resources.
- Media is organized as:

```text
YYYY/YYYY-MM/YYYY-MM-DD/
```

- Edited assets have their unmodified originals under:

```text
YYYY/YYYY-MM/YYYY-MM-DD/orig/
```

- Live Photo image resources are stored directly in the normal day directory.
- Live Photo companion videos are stored under:

```text
YYYY/YYYY-MM/YYYY-MM-DD/live/
```

- `orig/` is created only when necessary.
- `live/` is created only when necessary.
- Empty date directories are not retained unnecessarily.

### Resource Model

- Live Photo image and video resources remain associated with the same logical asset.
- Live Photo companion videos are not represented as independent standalone videos.
- RAW and other multi-resource assets are represented correctly.
- Original imported filenames are recovered whenever Photos contains them.
- Original media extensions are preserved.
- Filename collisions are deterministic and safe.

### Synchronization

- Capture date changes move all associated destination links correctly.
- Source deletions remove corresponding managed destination links.
- Unknown destination files are never deleted.
- Existing hard links are verified using filesystem identity.
- Re-running without source changes performs no unnecessary filesystem mutations.
- Cross-filesystem hard-link attempts fail clearly instead of silently copying.

### Database

- `photos.sqlite` describes the complete current synchronized state.
- SQLite contains normalized important metadata.
- Complete extracted metadata is retained as JSON.
- Deleting the destination SQLite database does not prevent synchronization.
- SQLite can be completely rebuilt from the source and destination.

### Metadata

- HEIC metadata works without external tools where supported by the selected Go library.
- Video/QuickTime metadata can use ExifTool fallback.
- Metadata extraction is incremental where safe.

### iCloud

- Missing iCloud resources are detected.
- Missing resources are not treated as valid local files.
- The program never automatically requests downloads from iCloud.

### Safety

- `-dry-run` shows intended changes without modifying anything.
- Uncertain ownership produces a conflict rather than destructive deletion.
- An interrupted synchronization can be safely reconciled by the next run.

## 40. Architectural Principle

Keep these concepts strictly separated:

```text
Apple Photos logical model
        |
        v
normalized Asset / Resource model
        |
        v
destination synchronization model
```

The synchronization engine must not understand Apple Core Data tables directly.

The Photos database reader must not decide which destination files to create or delete.

The metadata reader must not contain synchronization logic.

The destination catalog must not contain Photos-specific database queries.

This separation is important because the Photos SQLite schema is private, undocumented, and can change between macOS/Photos releases.

---

## 41. Primary Safety Principle

At every stage prefer reconciliation over assumptions.

The program must be able to determine the current state by examining:

```text
Photos Library
+
destination filesystem
```

The destination:

```text
photos.sqlite
```

is an optimization and metadata catalog, not the ultimate source of truth.

A missing, outdated, corrupted, or partially written destination database must never cause valid media hard links to be incorrectly deleted.

When synchronization cannot confidently determine ownership or resource identity:

```text
DO NOT DELETE
```

Report a conflict instead.

The source Photos library is always considered read-only and must remain unchanged regardless of synchronization success or failure.
